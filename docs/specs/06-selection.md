# 06. 선택 기반 편집 (탭 선택 · 오버레이 컨트롤)

- 상태: **Implemented** (2026-07-28)
- 관련: [스펙 03](03-editor.md)·[스펙 05](05-rotation.md)의 조작 모델을 대체. 배경: 실기기에서
  핀치(줌)와 트위스트(회전)가 충돌해 회전이 어렵다는 피드백 (2026-07-28)

## 인터랙션 모델

- **사진 있는 슬롯 탭 = 선택 토글.** 선택 시:
  - 슬롯 rect에 **여백 없이 딱 붙는 흰 테두리** (참고 이미지 스타일, 안쪽 여백 없음)
  - **고스트(35%) 상시 표시** — 조작 중이 아니어도 잘리는 영역이 보인다
  - 오버레이 버튼: **✕(우상단) = 사진 삭제**(빈 슬롯으로 복귀 — 2026-07-28 정정, 변경 이력),
    **📷(하단 중앙→슬롯 아래) = 사진 교체**(파일 선택), **회전 컨트롤(상단 중앙)**
- **조작은 선택 상태에서만**: 1지 드래그 = 이동, 핀치/휠 = 줌 (트위스트 회전 제거 — 회전은 전용
  컨트롤), Shift+휠 = 회전(데스크톱 보조)
- **빈 슬롯 탭 = 기존대로 바로 파일 선택** (선택 개념 없음)
- **선택 해제**: 사진 재탭, 슬롯 밖(캔버스 배경) 탭, **캔버스 바깥 페이지 영역 탭**
  (2026-07-29 추가 — 슬롯이 캔버스 너비를 꽉 채우는 프레임은 캔버스 안에 해제할 배경이 없다),
  비율 전환·홈 이동 시 자동 해제 (✕는 해제가 아니라 삭제 — 삭제하면 선택도 함께 풀린다)
- 사진 교체는 "선택 → 📷"로 이동 (기존 "재탭=즉시 교체"는 폐지 — 탭이 선택으로 대체)

## 상태 모델 변경 — 편집 상태 전부 사진 속성으로

"각도는 유지되는데 확대는 유지되지 않는다" + "post에서 보이게 한 부분이 story에서 다르다"
피드백 반영 (2026-07-28 실기기 확인):

- **슬롯 공유(사진 속성)**: `rotation` + `zoom`(cover 대비 상대 배율) +
  **`focal`(슬롯 중앙에 오는 사진 지점 — 사진 좌표계, 신규)**
- 실제 배율 = `minScale(θ, rect) × zoom`, 오프셋 = 초점이 슬롯 중앙에 오도록 역산 —
  비율 전환 시 같은 부분·확대감·각도가 그대로 유지되고, 슬롯 크기 차이는 minScale·클램프가 흡수한다
- 비율별 독립 저장은 없다 (초기 설계의 "오프셋만 비율별 독립"은 폐기 — 아래 변경 이력)
- 사진 교체 시 rotation·zoom·focal 전부 초기화 (기존 규칙 유지)

## 렌더 구조

- 선택 테두리·오버레이 버튼은 **셋째 레이어(listening)** — 내보내기(레이어 0만 래스터화)와
  시각 회귀(레이어 0 비교)에서 구조적으로 제외
- 버튼 스타일: 참고 이미지처럼 원형 배지 (✕ = 잉크 배경·흰 아이콘, 📷 = 흰 배경·잉크 아이콘)

## 수용 기준

1. 사진 탭 → 테두리·고스트·버튼 표시, 재탭/바깥 탭 → 해제, ✕ → 사진 삭제(빈 슬롯 복귀) (E2E)
2. 선택 상태에서만 드래그·줌이 동작하고, 미선택 사진은 탭해도 위치가 변하지 않는다
3. 📷로 교체 시 새 사진이 cover·무회전으로 들어간다
4. 회전 컨트롤로 임의 각도 회전 (90° 스냅 유지), 빈틈 없음 불변식 유지
5. **비율 전환 시 위치(초점)·확대감·각도가 모두 유지**된다 (E2E 픽셀 검사)
6. 선택 UI가 내보내기 PNG·시각 회귀에 나타나지 않는다
7. 기존 무선택 플로우(빈 슬롯 첨부, 다운로드, 초기화)는 무회귀

## 사용자 확인 결과 (2026-07-28)

- **회전 컨트롤 = 궤도 핸들** — ⟳ 핸들을 잡고 원을 그리듯 드래그하면 사진이 따라 돈다 (90° 스냅 유지)

## 변경 이력

- 2026-07-28 구현 확정: 📷 버튼을 슬롯 안쪽 하단 → **슬롯 바깥 아래**로 이동.
  모바일의 작은 슬롯(frame03 등)에서 버튼이 슬롯 중앙을 덮어 탭·드래그를 가로챘다.
  ⟳(위)·📷(아래)가 슬롯 바깥에 대칭 배치되어 시각적으로도 정돈됨.
- 2026-07-28 실기기(iOS Safari) 피드백 2건 반영:
  - **✕·📷 버튼이 실기기에서 무반응** → 액션 실행을 pointerdown(누르는 순간)에서
    **탭 완료 시점(click/tap/pointerclick 3종 바인딩 + 400ms 중복 제거)**으로 이동.
    iOS는 한 탭에 pointer/touch/호환 mouse 이벤트를 모두 발사하고, 터치의 user activation은
    pointerup/touchend에야 부여되어 pointerdown 시점의 `input.click()`(파일 선택창)이 무시된다.
    보조: 버튼 히트 영역을 시각 원(16~18px)보다 큰 투명 원(24px, 48pt 타깃)으로 확장,
    ⟳ 핸들·배경 탭 해제에 touch 이벤트 폴백 추가. WebKit(iPhone 13) 터치 + Chromium
    모바일 `touchscreen.tap` E2E로 검증.
  - **post에서 편집한 위치가 story에서 다르게 보임** → 비율별 독립 오프셋을 폐기하고
    **공유 초점(focal)** 모델로 전환 (위 "상태 모델 변경" 절 갱신). 스토어는
    `focals[slotId]`(사진 좌표계)만 저장하고 렌더 시 각 비율의 slot rect로 역산·클램프한다.
- 2026-07-28 사용자 확인: **✕ = 선택 해제가 아니라 사진 삭제** (빈 슬롯으로 복귀,
  비트맵 반환·편집 상태 초기화·선택 해제 동반). 초기 스펙의 "✕=해제"는 의도 오해였음.
  선택 해제 경로는 재탭·배경 탭·비율 전환으로 충분.
- 2026-07-29 기획 피드백 반영:
  - **제스처 표면**: 드래그/핀치/휠 터치 영역을 슬롯 rect에서 **선택된 사진의 전체 바운딩
    박스(고스트 영역 포함)**로 확장 (2차 확장은 아래 2026-07-29 항목). 선택 컨트롤 레이어에 사진과 같은 변환의 투명 Rect를 깔고,
    탭은 아래 슬롯 기준으로 기존 의미(재탭=해제, 다른 사진=선택 전환, 빈 슬롯=첨부, 배경=해제)를
    재현한다. 버튼(✕/📷/⟳)은 표면 위에 있어 우선.
  - "Tap a slot to add a photo" 하단 문구 제거.
  - 파일 input을 display:none → **시각적 숨김(fixed 1px)**으로 변경 — display:none이면
    iOS Safari가 파일 메뉴 뒤에 앵커 프리뷰(원형 블롭)를 그린다.
  - (2차) 1px 앵커로도 원형 폴백 판이 잠깐 떴다 사라짐 → 슬롯 rect 전체를 앵커로 제공했더니
    **슬롯만 한 대형 판**이 그려짐(실기기 확인). /debug/picker 4방식 비교(실기기 영상 판독)로
    **판 크기 = 앵커 rect 크기**임을 확정 — 트리거 방식(프로그램 click vs label/직접 탭)은 무관.
  - (3차) 앵커 48px 축소 — 실기기에서 여전히 블롭. input의 위치·크기는 무관했다.
  - (4차, 근본 원인 확정·재구현) **iOS는 숨김 input의 파일 메뉴를 input이 아니라
    "활성화를 일으킨 요소"에 앵커링한다.** 캔버스 탭 → `input.click()`이면 활성화 요소가
    캔버스 전체라 캔버스 크기의 판이 그려진다 (블롭 색이 매번 캔버스 배경색이었던 이유,
    /debug/picker가 4방식 모두 깨끗했던 이유 — 활성화 요소가 작은 버튼). 해결:
    **파일 선택 트리거를 전부 DOM 버튼으로 재구현** — 빈 슬롯 + 배지(Konva UI 레이어 →
    DOM 오버레이 버튼, 슬롯 중앙 44px)와 📷 교체 버튼(Konva → DOM `ReplaceButton`)이
    `input.click()`을 호출한다. 캔버스의 빈 슬롯 탭은 더 이상 파일 선택을 열지 않는다
    (배지가 유일한 진입점). ✕·⟳·선택 테두리·제스처는 Konva 유지.
  - 저장 플로우 변경은 [스펙 04](04-export.md) 변경 이력 참조 (iOS 공유 시트).
  - **캔버스 바깥 페이지 영역 탭 = 선택 해제** — 슬롯이 프레임을 꽉 채우는 템플릿은
    프레임 안에 "해제할 배경"이 없다는 피드백.
- 2026-07-29 (2차) 기획 피드백 — **스테이지를 프레임이 아니라 편집 영역 전체로 확장**:
  - 배경: ① 프레임 밖으로 넘치는 고스트가 캔버스 경계에서 잘렸다(디자이너: 잘리지 않기를 원함)
    ② 구멍이 작은 프레임은 사진 위에서만 핀치가 되어 배율 조정이 어려웠다.
  - 구조: `<Stage>`가 편집 영역(컨테이너) 전체를 덮고, 프레임은 그 안에 중앙 배치(정수 px 스냅).
    세 레이어의 원점을 프레임 좌상단으로 옮겨 템플릿 좌표(placement.rect)는 그대로 쓴다.
    메인 레이어만 `clipFunc`로 프레임+라운드 코너에 자르고(내보내기 시 해제), **고스트·선택
    컨트롤 레이어는 클립하지 않아 프레임 밖에도 그려진다.** 프레임 카드의 그림자·라운드는
    스테이지 뒤 DOM이 담당. 관측 가능한 넘침 범위는 편집 영역까지 (뷰포트가 좁아 프레임이
    폭을 꽉 채우면 좌우 여백이 없다).
  - 제스처: 표면이 **편집 영역 전체**로 확장 — 핀치/휠 줌은 사진 밖 어디서 시작해도 동작하고,
    한 손가락 드래그는 사진(고스트 포함) 위에서 시작한 경우만 이동으로 해석한다(회전된
    바운딩 박스 히트 테스트). 그 밖에서 시작한 한 손가락 탭은 기존대로 해제.
  - ✕·⟳·📷 클램프 범위도 프레임 → 편집 영역으로 확장(프레임 밖 여백까지 활용).
  - E2E: 프레임 원점·배율을 `data-frame-*` 속성으로 노출해 템플릿 좌표를 화면 좌표로 환산한다
    (시각 회귀는 프레임 영역만 잘라 비교).
